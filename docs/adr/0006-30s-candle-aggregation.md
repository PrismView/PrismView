# ADR-0006 · 30초봉 집계 규칙 — SQL 집계, 종목×월 실행, 수집된 범위 안의 완전한 버킷만

- 상태: 채택
- 날짜: 2026-11-11
- 저장소: [prismview-collector](https://github.com/PrismView/prismview-collector) #43
- 관련: M4(30초봉 집계 + 정합성), M5(증분 수집), M6(Parquet 내보내기), [ADR-0002](0002-30s-candle.md), [ADR-0005](0005-1s-candle-retention.md), prismview-collector #6

## 맥락

- [ADR-0002](0002-30s-candle.md)는 30초봉을 만드는 식(버킷 시작, OHLCV 규칙)을 정했다. 하지만 SQL로 시가·종가를 어떻게 구할지, 어느 범위를 어떤 단위로 집계할지, 1초봉이 30개 미만인 버킷을 어떻게 다룰지는 정하지 않았다.
- M3 백필로 `candle_1s`에 약 4,131만 행이 있다 (BTC 20,629,059행 / ETH 20,685,147행, 2026-03-13 ~ 2026-11-07). `candle_30s`는 비어 있고, 집계하면 약 138만 행이 된다.
- #6에서 OKX는 체결이 없는 초도 거래량 0 봉으로 채운다는 것을 확인했다. 따라서 정상적인 30초 버킷에는 1초봉이 정확히 30개 있고, **30개 미만이면 누락**이다.
- 수집 범위의 시작과 끝은 30초 경계와 맞지 않는다 (예: BTC 시작 13:25:02, 끝 07:42:40). 이 경계의 버킷은 누락이 아니라 **수집 범위 밖**이다.
- 같은 집계를 M5 증분 수집에서도 짧은 범위로 반복 실행해야 한다.

## 검토한 선택지

**버킷 계산**

| 선택지 | 판단 |
|---|---|
| **A. 정수 계산 (`ts / 30000 * 30000`)** | **채택** |
| B. 날짜 타입 경유 (`to_timestamp`, `date_bin`) | 탈락. 시간대 해석·타입 변환 함정이 생긴다 (V2 파티션 경계의 `+00` 생략 사례). ts가 이미 epoch ms라 변환할 이유가 없다 |

**시가·종가 구하기**

| 선택지 | 판단 |
|---|---|
| **A. `(array_agg(open ORDER BY ts))[1]`** | **채택**. GROUP BY 한 번에 끝나고, 버킷당 원소가 30개라 배열 비용은 무시할 만하다 |
| B. 윈도 함수 `FIRST_VALUE` | 행을 줄이지 않아 DISTINCT 등 한 단계가 더 필요하다 |
| C. 버킷별 `min(ts)`/`max(ts)`로 다시 조인 | 테이블을 두 번 읽는다 |

**실행 단위**

| 선택지 | 판단 |
|---|---|
| A. 전 기간을 SQL 한 문장으로 | 탈락. 실패하면 전부 롤백되고, 끝날 때까지 진행 상황을 알 수 없다. M5용 범위 쿼리를 따로 만들어야 한다 |
| **B. 범위를 받는 쿼리 + 종목×월 단위 호출** | **채택** |

**범위 경계와 30개 미만 버킷**

| 선택지 | 판단 |
|---|---|
| A. 30개 미만 버킷은 버린다 | 탈락. 누락이 에러 없이 사라져 백테스트를 조용히 왜곡한다 |
| B. 1초봉이 있는 버킷은 전부 저장 | 탈락. 수집 범위 시작·끝의 잘린 버킷이 가짜 누락으로 잡힌다 |
| **C. 수집 범위에 완전히 들어가는 버킷만 집계하고, 그 안에서는 30개 미만도 저장** | **채택** |

**"하루" 경계**

| 선택지 | 판단 |
|---|---|
| **A. UTC 자정** | **채택** |
| B. KST 자정 | 탈락. 저장·파티션·버킷 경계와 9시간 어긋나 계산마다 보정이 필요하다 |

## 결정

1. **버킷 시작 = `ts / 30000 * 30000`** (ADR-0002와 같은 식)
   - 정수 계산만 쓰고 날짜 타입을 거치지 않는다.
   - PostgreSQL 정수 나눗셈은 0 쪽으로 버리지만 ts > 0(CHECK)이라 내림과 같다.

2. **집계는 DB 안에서 SQL(`INSERT ... SELECT ... GROUP BY`)로 한다**
   - open = `(array_agg(open ORDER BY ts))[1]`, close = `(array_agg(close ORDER BY ts DESC))[1]` (PostgreSQL 배열은 1부터 시작)
   - high = `MAX`, low = `MIN`, 거래량 3종 = `SUM`, `src_cnt` = `COUNT(*)`
   - `ON CONFLICT (inst_id, ts) DO UPDATE`로 재실행해도 같은 결과를 보장한다.

3. **집계 쿼리는 `(inst_id, from, to)`를 받고, 호출하는 쪽이 범위를 나눈다**
   - 범위 조건은 ts 원본에 건다: `ts >= :from AND ts < :to` (파티션 프루닝과 PK 인덱스가 동작하게)
   - 백필은 종목×월 단위로 나눠 호출하고, 단위마다 트랜잭션 하나
   - 월 경계(UTC 자정)는 항상 30초 경계와 맞으므로(86,400,000 = 30,000 × 2,880) 버킷이 잘리지 않는다.
   - M5 증분 수집은 같은 쿼리를 짧은 범위로 호출한다.

4. **집계 범위 = 수집된 구간에 완전히 들어가는 버킷**
   - 시작(포함) = `min(ts)`를 30초 단위로 올림
   - 끝(제외) = `max(ts) + 1000`을 30초 단위로 내림
   - 범위 안의 버킷은 1초봉 개수와 관계없이 저장한다. **범위 안에서 `src_cnt < 30`이면 누락**이다 (#6 전제).
   - "버킷이 끝났는가"는 현재 시각이 아니라 **DB에 받은 데이터**로 판단한다.
   - 1초봉이 0개인 버킷은 `candle_30s`에 행이 생기지 않는다. 그래서 누락 탐지는 `src_cnt`가 아니라 1초봉 ts 간격으로 한다.

5. **"하루" 경계는 UTC 자정**
   - 암호화폐는 전 세계에서 24시간 거래되어 특정 나라의 시간대가 기준이 될 수 없다. UTC는 어느 나라의 법정 시간도 아닌 중립 기준이다.
   - 저장(ts), 파티션 경계, 30초 버킷이 모두 UTC라 경계가 한 줄로 맞는다 (UTC 하루 = 30초 버킷 2,880개).
   - 계산 기준일 뿐 표시 시간대와는 별개다. 화면에서는 KST로 보여 줄 수 있다.
   - 적용은 M6.

6. **저장 범위와 사용 범위를 분리한다**
   - `candle_30s`에는 위 규칙대로 완전한 버킷을 전부 저장한다.
   - 용도별 범위는 꺼낼 때(M6) 고른다.
     - 단순 백테스트: 마지막 완전한 30초 버킷까지
     - 지표 로직 분석: 마지막 완전한 하루까지 (`max(ts) + 1000`을 86,400,000 단위로 내림, 시작은 `min(ts)`를 86,400,000 단위로 올림)

## 결과

좋아지는 점

- 30개 미만 버킷이 사라지지 않고 `src_cnt`로 남아, 누락이 조용히 묻히지 않는다.
- "범위 안에서 `src_cnt < 30` = 누락"이라는 규칙이 수집 범위 경계 때문에 깨지지 않는다.
- 월 단위로 실패를 격리하고 진행 상황을 볼 수 있다. upsert라 재개 기능이 따로 필요 없다 (다시 실행하면 된다).
- 백필(M4)과 증분 수집(M5)이 같은 쿼리를 쓴다.
- 1초봉을 Java로 가져오지 않아 4,131만 행이 네트워크를 오가지 않는다.

감수하는 점

- 집계 로직이 SQL에 있어서 DB 없는 단위 테스트로는 검증할 수 없다 → Testcontainers로 테스트한다.
- `array_agg ... ORDER BY`, `ON CONFLICT`는 PostgreSQL 문법이다 ([ADR-0001](0001-postgresql.md)로 DB를 정했으므로 받아들인다).
- 수집 범위 끝의 미완성 버킷은 다음 수집 전까지 저장되지 않는다 (최신 30초봉이 최대 한 버킷 늦다).
- 수집 범위 시작의 잘린 버킷(최대 29초분)은 30초봉으로 남지 않는다. 1초봉 원본에는 남아 있다.

## ADR-0002와의 관계

이 ADR은 0002를 대체하지 않고 **구체화**한다. 0002는 "채택" 상태 그대로 유효하다.

- 같은 점: 버킷 시작 식, OHLCV 규칙, `confirm = 1`인 1초봉만 집계
- 구체화한 점: 0002의 "1초봉 30개가 모두 있을 때만 완전으로 표시"를 "버리지 않고 저장, `src_cnt`로 표시"로 정하고, 범위 규칙(결정 4)으로 30개 미만의 의미를 "누락"으로 고정했다.
- 달라진 점: `known_gaps`의 범위. 0002는 OKX 제공 시작점 이전 구간을 `known_gaps`에 남기려 했다. 이 ADR부터 `known_gaps`는 **집계 범위 안에서 다시 받아도 비어 있는 곳**만 기록한다. 범위 밖은 결정 4의 범위 규칙으로 처리한다.
## 다시 검토할 조건

- OKX가 체결 없는 초를 거래량 0 봉으로 채우지 않게 바뀌면 (#6 전제가 깨짐 → `src_cnt < 30` = 누락 규칙을 다시 정한다)
- M5 증분 수집에서 집계 쿼리가 수집 주기에 비해 너무 느리면 (실행 단위·방식을 다시 정한다)
- 전략 시간봉이 30초에서 바뀌거나 다른 초 단위 봉(5·10·15초)을 함께 만들게 되면 (버킷 크기를 매개변수로 뺄지 정한다)
- 저장소가 PostgreSQL에서 바뀌면 (`array_agg ... ORDER BY`, `ON CONFLICT`를 다시 작성한다)
