# ADR-0004 · 백테스터 입력으로 Parquet 내보내기

- 상태: 채택
- 날짜: 2026-10-27
- 저장소: [prismview-collector](https://github.com/PrismView/prismview-collector) → [prismview-backtester](https://github.com/PrismView/prismview-backtester) (예정)

## 배경

수집기는 Java, 백테스터는 Python이다. 백테스트는 수개월 30초봉을 처음부터 끝까지 순서대로 읽는다(전 구간 스캔). DB를 직접 열어 읽으면 스키마·드라이버·실행 환경이 백테스터에 묶이고, "어제와 같은 입력인지"를 증명하기 어렵다.

## 결정

PostgreSQL은 수집기의 **운영 저장소**로 두고, 백테스트에 쓸 구간은 **Parquet 파일로 내보낸다.**

- 기본 export 대상은 확정된 30초봉이다. 필요하면 1초봉도 같은 형식으로 뺀다.
- 파일은 종목·기간이 이름에 드러나게 둔다. 예: `BTC-USDT-SWAP_30s_2026Q1.parquet`
- 백테스터는 DB에 접속하지 않고 이 파일만 읽는다.

## 검토한 대안

| 대안 | 쓰지 않은 이유 |
| --- | --- |
| 백테스터가 PostgreSQL을 직접 조회 | 단순하지만 Java 스키마 변경이 Python을 깨뜨린다. 재현하려면 DB 스냅샷이 필요하다. |
| CSV | 호환은 좋지만 컬럼 타입·압축·부분 컬럼 읽기가 Parquet보다 약하다. |
| 조회 API만 제공 | 차트에는 맞다. 수백만 행 스캔을 HTTP로 하면 백테스트가 네트워크  Bound가 된다. |

## 이유

1. **재현성.** 같은 Parquet를 넣으면 같은 거래 내역이 나와야 한다. 파일을 커밋하거나 날짜를 적어두면 회귀 테스트가 된다.
2. **언어 경계.** Java 수집기와 Python 백테스터가 DB 스키마를 공유하지 않는다. 계약은 파일 스키마 하나다.
3. **읽기 패턴.** 열 저장·압축이라 종가·고가·저가만 스캔하는 백테스트에 잘 맞는다. DuckDB/polars가 바로 읽는다.

## 결과 · 대가

- 수집기에 export 경로가 하나 더 생긴다. 운영 진실의 원천은 여전히 PostgreSQL이다.
- Parquet는 스냅샷이므로, 누락을 메운 뒤에는 해당 기간 파일을 다시 만들어야 한다.
- 차트용 조회 API는 나중에 웹이 붙을 때 PostgreSQL 위에서 별도로 둔다. Parquet가 API를 대체하지는 않는다.

## 다시 검토할 조건

백테스터와 수집기를 같은 프로세스에서 돌리거나, 실시간 시그널과 백테스트가 초 단위로 같은 DB를 봐야 하면 파일 단계를 줄이고 조회 API를 공통 입력으로 승격한다.
