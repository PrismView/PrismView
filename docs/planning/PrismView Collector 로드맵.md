## 1. 이슈 하나를 처리하는 흐름 (모든 마일스톤 공통)

```
보드에서 카드 In progress로 이동
  → 이슈 페이지 Development > Create a branch (feat/<번호>-<설명>)
  → git fetch && git switch <브랜치>
  → 작업 (실패를 먼저 예상하고 실행)
  → 커밋 → push → PR (본문: 무엇을 / 왜 / 확인한 것 / 알려진 문제 / Closes #번호)
  → 리뷰어 계정(lgtm-minseok)으로 Files changed 검토 → Approve
  → Merge → 원격 브랜치 삭제
  → git switch main && git pull && git branch -d <브랜치>
  → 보드 Done · 마일스톤 진행률 확인
```

- 아직 존재하지 않는 이슈는 **번호 대신 제목**으로 언급한다 (PR도 번호를 소비하므로 미래 번호는 어긋난다).
- 결정이 생기면 허브 레포 `docs/adr/`에 ADR 한 장.

## 3. M2 — OKX 1초봉 조회

**목표**: `history-candles?bar=1s`를 호출해 한 페이지(최대 100개)를 `List<Candle>`로 받는다.

**예상 이슈**
- 도메인 레코드 `Candle` 작성 (`BigDecimal`, `confirm` 필드)
- OKX 응답 DTO와 Jackson 매핑
- `RestClient`로 history-candles 호출
- OKX 응답 목 서버로 단위 테스트 (MockWebServer / WireMock)

**미리 알아 둘 것**
- `RestClient`는 `spring-web`에 있다 → 추가하면 Tomcat이 뜬다 → 서버가 필요 없으면 `spring.main.web-application-type=none`
- Boot 4는 **Jackson 3**이라 Boot 3 예제와 import 패키지가 다를 수 있다
- 응답은 **최신순**, 값은 전부 **문자열**, `confirm`이 `"1"`인 봉만 저장 대상
- `BigDecimal`은 문자열로 생성, 비교는 `compareTo`

> 🤔 **생각해 볼 질문**: OKX를 실제로 호출하는 테스트만 있으면 안 되는 이유는?
>
> **해설**: 네트워크가 끊기거나 OKX가 점검 중이면 내 코드와 무관하게 테스트가 실패한다. 응답도 매번 달라서 "같은 입력 → 같은 결과"를 검증할 수 없다. 응답 JSON을 파일로 저장해 목 서버가 돌려주게 하면, 매핑 로직만 정확히 검증할 수 있다.

## 4. M3 — 1초봉 3개월 백필 ⚡ 시간이 가장 중요한 단계

**목표**: 최근 3개월 1초봉을 끝까지 받아 저장한다. 중간에 꺼져도 이어서 받는다.

**규모 추정**

| 항목 | 값 |
|---|---|
| 행 수 | 2종목 × 약 90일 × 86,400초 ≈ **약 1,555만 행** |
| 호출 수 | ÷ 100개/요청 ≈ **약 15.5만 회** |
| 호출 제한 | history-candles **2초당 20회** (IP 기준) |
| 예상 소요 | 한도 80%로 잡으면 **약 5시간** |

**예상 이슈**
- `after` 커서 페이지네이션 (다음 커서 = 응답의 **가장 오래된** ts)
- 레이트 리미터 직접 구현 (토큰 버킷) → 이후 Bucket4j 등으로 교체 검토
- 재시도: 429·5xx·네트워크 오류만, 지수 백오프, 최대 횟수
- JdbcTemplate 배치 upsert (`ON CONFLICT ... DO UPDATE`)
- 중단 후 재개: 진행 상태를 **DB의 min(ts)** 에서 다시 계산
- 1초봉 테이블 (M1에서 정한 보관 방식대로)

> 🤔 **생각해 볼 질문**: 커서가 전진하지 않는 버그가 생기면 어떤 일이 일어날까?
>
> **해설**: 같은 페이지를 무한히 다시 받는다. upsert라 데이터는 깨지지 않지만 호출 제한만 소모하고 백필은 끝나지 않는다. "이번 커서가 이전 커서보다 반드시 작다"를 검사하고, 아니면 예외를 던지는 방어 코드와 그 단위 테스트가 필요하다.

## 5. M4 — 30초봉 집계 + 정합성

**목표**: 1초봉을 30초봉으로 접어 `candle_30s`에 저장하고, 누락을 찾아 기록한다.

**예상 이슈**
- 30초 집계: 버킷 `ts / 30000 * 30000`, open=첫 봉, close=마지막 봉, high=max, low=min, 거래량=sum
- **완료된 버킷만** 집계 (진행 중인 30초는 건너뜀)
- 누락 탐지: `LAG(ts) OVER (PARTITION BY inst_id ORDER BY ts)`
- `known_gaps` 테이블: 재요청해도 비는 구간(점검 등) 기록 → 무한 재요청 방지
- 값 검증: high ≥ max(open, close), low ≤ min(open, close), 음수 금지, 경계 정렬(`ts % 30000 = 0`)
- **교차 검증**: 30초봉 2개를 합친 값 vs OKX 1분봉 (필요 구간만 그때그때 조회)
- 1초봉 단기 보관이면 오래된 1초봉 삭제 작업

> 🤔 **생각해 볼 질문**: Cursor 뼈대의 집계 코드는 1초봉 29개짜리 버킷을 어떻게 처리했고, 그게 왜 위험했나?
>
> **해설**: 30개가 아니면 **조용히 버렸다.** OKX가 체결 없는 초를 생략한다면 한산한 시간대의 30초봉이 에러 없이 사라진다. 누락은 에러를 내지 않고 백테스트 결과를 조용히 왜곡한다. 그래서 M1의 빈 초 확인 결과로 규칙을 정하고, 버리는 대신 `src_cnt`처럼 근거를 남기는 쪽으로 설계한다.

## 6. M5 — 주기적 증분 수집

**목표**: 앱을 켜 두면 마지막 저장 시점부터 자동으로 따라잡는다.

**예상 이슈**
- 증분 로직: **"DB의 마지막 확정 ts 이후"** 를 받는다 ("어제 하루치" 방식 금지)
- 실행 방식: 수동 실행 커맨드 → 안정되면 `@Scheduled(fixedDelay)`
- 동시 실행 방지 (단일 스케줄러 스레드)
- 실행 주기: 하루 1회 이상 (하루치 ≈ 1,700회 호출 ≈ 3~4분)

**운영 규칙**
- 노트북을 **3개월 넘게** 안 켜면 데이터 손실 → 최소 월 1회는 실행
- 장기적으로 상시 실행 환경(홈서버, 클라우드) 검토

> 🤔 **생각해 볼 질문**: `fixedRate` 대신 `fixedDelay`를 쓰는 이유는?
>
> **해설**: `fixedRate`는 시작 시점 기준이라, 작업이 주기보다 길어지면 밀린 실행이 바로 이어 붙는다. 수집처럼 실행 시간이 들쭉날쭉한 작업은 "끝난 뒤 일정 시간 쉬고 다시"인 `fixedDelay`가 안전하다.

## 7. M6 — 백테스트 연결

**목표**: PostgreSQL의 30초봉을 Parquet로 내보내 Python 백테스터에서 읽는다.

**예상 이슈** (일부는 `prismview-backtester` 레포에서)
- 내보내기 스크립트: Python 또는 DuckDB (`postgres` → `parquet`)
- 파일 단위: 종목별 · 월별, 파일명에 기간과 생성 시각
- 완전성 정보 포함 (불완전 버킷 표시)
- Python에서 pandas/polars로 읽기 확인

> 🤔 **생각해 볼 질문**: DB를 바로 읽지 않고 Parquet 스냅샷을 쓰는 이유는?
>
> **해설**: 수집기가 계속 데이터를 추가하므로 DB를 직접 읽으면 실행할 때마다 마지막 구간이 달라진다. 결과 차이가 전략 때문인지 데이터 때문인지 구분할 수 없다. 스냅샷을 고정하면 "같은 입력 → 같은 결과"가 보장된다.
